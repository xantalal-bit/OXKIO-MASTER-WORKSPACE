## Correcciones

- **P1-A (EPERM/rename en Windows).** El rename se reintenta de forma acotada ante EPERM/EBUSY/EACCES. Si aun así falla, el archivo en disco decide:
  - si contiene el snapshot cargado → `store_write_failed` (determinista; se libera el lock);
  - si contiene el nuevo → éxito;
  - cualquier otro contenido → `commit_unknown`.
  Mientras se publica, un marcador `.publish` pide a los lectores ceder un instante. Es solo una pista: se ignora si es antiguo, y la corrección depende de la verificación. Un `commit_unknown` real marca el lock `uncertain`. Ese lock no se recupera solo; requiere `recover()` explícito (owner/supervisor), que solo libera tras cargar el snapshot y verificar todos los sellos.
- **P1-B (lock huérfano).** El lock lleva metadatos: `{id, pid, host, acquiredAt, expiresAt, state}`.
  - Se recupera solo con evidencia: lease vencido Y titular inexistente en este host (PID muerto, o este proceso sin transacción con ese id).
  - Nunca se rompe un titular vivo, de otro host, ilegible ni `uncertain`.
  - La recuperación se serializa con un archivo guarda y solo elimina el mismo lock evaluado.
  - Lease por defecto: 10 s.
- **P1-C (`call_unknown`).** El bloqueo pasa a ser por *scope*: misión + tarea/fase, que todos los modelos de ese paso comparten.
  - La llamada incierta no se repite ni se sustituye por failover. Las misiones no relacionadas siguen.
  - Error propio `call_reconciliation_required`, con `status: CALL_RECONCILIATION_REQUIRED` y `transient: false`. Nunca es BUDGET_EXHAUSTED.
  - La misión queda `BLOCKED` con diagnóstico `call_reconciliation_required` / `RECONCILE_CALL`, y un mensaje propio que no menciona presupuesto.
  - `reconcileCall` (owner/supervisor, con `evidenceRef`) decide `charged` / `not_executed` / `uncertain`. Es idempotente; una decisión distinta sobre una llamada cerrada da `reconciliation_conflict`.
  - No está en la vista de gasto del reasoner, así que ningún modelo puede invocarla. No hay ruta HTTP ni reconciliación externa.
  - Una respuesta recibida cuyo settle no se confirma queda `claimed` (`settle_unconfirmed`): no se reserva de nuevo ni se cobra dos veces.
- **P1-D (saturación).** Retención determinista de los recibos cerrados (`settled`/`released`), conservando los más recientes: `retainSettledReceipts` (200) acotado a 1/10 de la capacidad del store.
  - Los más antiguos se pliegan en `cost-archive` por mes (contador, suma y cadena hash del recibo) antes de borrar el recibo y su índice.
  - Las llamadas reservadas, claimed y unknown nunca se compactan. Los agregados de día/misión no cambian.
  - Un recibo compactado no puede liquidarse otra vez (`reservation_unknown`).
- **P2-A.** Sobrecargo y reservas legadas usan `ledger_reconciliation_required` (no transitorio, nunca presupuesto). `clearOvercharge` es explícito, con evidencia, y conserva el gasto real.
- **P2-B.** `put`/`remove` esperan el lock de forma acotada. Una transacción con operación síncrona no cede el hilo con el lock tomado, así que no hay `store_busy` intraproceso. Si el lock lo retiene un `await` del mismo proceso, se falla de inmediato en vez de bloquear el hilo (sin deadlock).
- **P2-C.** Una estimación distinta para una reserva pendiente da `reservation_conflict` explícito: el paso se detiene sin llamar. Se libera con `reconcileCall('not_executed')`.
- **P2-D.** Solo se liquida una llamada `claimed` (`call_not_claimed` si no). Una reserva nunca reclamada solo se libera, nunca se cobra.
- **P2-E.** Si BEGIN falla, la conexión PostgreSQL se descarta (`release(true)`).
- **Retirada de una restricción del commit anterior:** un recibo ya cerrado (settled/released) permite un intento nuevo del mismo paso, y la reanudación desde WAIT_RESOURCE vuelve a funcionar. Una llamada abierta o incierta sigue bloqueando.
