## B. Stores bloqueantes

Bloquean Cliente Cero remoto 24/7 o multiusuario:

1. Approval Queue: una aprobación podría perderse o aprobarse dos veces entre instancias.
2. Operation/Execution Log: no existe reserva atómica durable de `idempotencyKey`.
3. Memory: las escrituras snapshot pueden pisarse y no hay separación por usuario.
4. OAuth token file: un único fichero local representa implícitamente a un sujeto.
5. Executive Agenda, Project Registry y Security Inventory: se escriben en filesystem
   durante el uso o incluso durante el arranque.
6. Strategic Memory: el módulo activo puede crear un store local no durable.
7. Audit: falta una fuente append-only compuesta y consultable.
8. Knowledge Stores: bloquean multiinstancia si se habilita adquisición/escritura remota.

No bloquean por sí solos si se mantienen en su autoridad actual: Google Calendar,
Drive/OneDrive, gobernanza Git, fixtures y configuración no secreta.

## Matriz Firestore vs PostgreSQL vs híbrida

| Criterio | Firestore | PostgreSQL gestionado | Híbrida Firestore + PostgreSQL |
|---|---|---|---|
| Consistencia | Fuerte para lecturas confirmadas | ACID; niveles de aislamiento configurables | Depende de coordinación entre dos sistemas |
| Transacciones | Atómicas sobre documentos; reintentos por contención | Multi-fila/multi-tabla; locks y Serializable disponibles | No hay transacción distribuida simple |
| Concurrencia | Buena si se evitan documentos calientes; contención reintenta/falla | Control explícito, MVCC, locks y constraints | Mayor superficie de carreras |
| Constraints | Validación en backend/rules; sin FK/unique relacional general | CHECK, NOT NULL, UNIQUE, PK, FK, exclusión | Constraints parciales por motor |
| Joins | No nativos | Nativos | Requiere fan-out o sincronización |
| Consultas | Indexadas y premodeladas | SQL flexible | Dos lenguajes y dos planes |
| Búsqueda textual | No full-text general; tokens o servicio adicional | Full-text nativo | Posible, pero duplica datos |
| Búsqueda vectorial | Disponible mediante índice vectorial; no ejecutada | Extensión/proveedor por decidir; estado `UNKNOWN` hasta elegir servicio | Complejidad superior |
| Reporting | Agregaciones y export; menos flexible para relaciones | SQL, vistas y agregación relacional | ETL necesario para visión conjunta |
| Auditoría append-only | Convención/IAM/backend | Trigger, permisos y tabla dedicada | Riesgo de divergencia |
| Coste | Por lecturas, escrituras, índices, almacenamiento y red | Instancia/compute, RAM, storage, backup, red y HA | Suma de ambos más integración |
| Escalabilidad | Serverless y automática; patrón de acceso condiciona índices | Vertical/réplicas/partición según proveedor | Alta, con mayor operación |
| Complejidad | Baja para CRUD documental; aumenta con relaciones y reglas backend | Mayor provisión inicial, modelo más directo para OXKIO | Máxima |
| Portabilidad | Modelo/API específicos | SQL y dump con alta portabilidad entre proveedores | Baja por dos dependencias |
| Aislamiento multiusuario | Jerarquía tenant + filtros; Admin SDK omite Security Rules | `tenant_id` obligatorio + RLS + filtros | Debe demostrarse dos veces |

## D. Modelo multiusuario propuesto

### Identidad y pertenencia

- `userId`: UID verificado por Firebase Authentication; nunca aceptado desde el body.
- `tenantId`: identificador interno resuelto por membresía; obligatorio en toda fila o
  ruta operativa.
- `membership`: `(tenantId, userId, role, status, createdAt, revokedAt)`.
- Roles iniciales contractuales: `owner`, `admin`, `operator`, `reviewer`, `viewer`.
- El backend deriva la identidad y abre la transacción con el `tenantId` autorizado.
- No se implementa autenticación nueva en 5C.7B.2.

### Ownership y permisos

| Capacidad | owner/admin | operator | reviewer | viewer |
|---|---|---|---|---|
| Perfil y membresías | administrar | leer propia | leer propia | leer propia |
| Aprobaciones | crear/decidir | crear | decidir si está autorizado | leer sanitizado |
| Operaciones | reservar/completar mediante servicio | solicitar | leer estado | leer estado sanitizado |
| Memoria | leer/escribir/exportar/borrar según política | leer/escribir propia | leer autorizada | leer autorizada |
| Auditoría | leer/exportar; nunca editar | generar eventos | leer | lectura limitada |
| OAuth | conectar/revocar propio; administrar política | conectar/revocar propio | sin token | sin token |

La autorización fina se mantiene en el backend. Si se usa PostgreSQL, RLS es una segunda
barrera y no sustituye validación de dominio. Si se usa Firestore desde Admin SDK,
Security Rules no protegen las llamadas servidoras: todos los paths y filtros de tenant
deben imponerse y probarse en el backend.

### Trazabilidad, consentimiento y derechos

- Cada entidad operativa incluye `tenantId`, `userId`, `createdAt` y actor autorizado.
- Cada transición crítica emite un `eventId` único y correlación con aprobación/operación.
- `consent`: finalidad, versión, estado, fecha de otorgamiento/revocación y evidencia,
  nunca texto libre sensible.
- `dataSubjectRequest`: exportación o borrado, alcance, estado, autoridad y evidencia.
- Exportación: dataset versionado por tenant/user, checksum y manifiesto, sin secretos.
- Borrado: primero revocar ejecución/tokens, después aplicar retención legal y registrar
  tombstone de auditoría sin conservar contenido privado.
- Memoria: clave y consultas siempre por `(tenantId,userId)`; no búsqueda global implícita.
- OAuth: referencia lógica `(tenantId,userId,provider)` en el dominio; token, ciphertext,
  versión de clave y material criptográfico en el gestor de secretos futuro.

## E. POC comparable

La POC está aislada en `backend/repositories/poc/` y no se conecta al runtime oficial.
Usa un dataset de 1.144 bytes, sin datos reales, con:

- un tenant y usuario sintéticos;
- una aprobación `email_draft`;
- una operación con `idempotencyKey`;
- una memoria;
- un evento de auditoría;
- un tenant aislado de restauración;
- `executionEnabled=false` y `SAFE_DRAFT_ONLY`.

El contrato ejecuta las mismas operaciones:

1. inicializar scope tenant/user;
2. crear aprobación;
3. aprobar condicionalmente;
4. reservar `idempotencyKey`;
5. iniciar y completar operación;
6. rechazar reserva duplicada;
7. guardar y buscar memoria;
8. append de auditoría;
9. consultar auditoría por tenant/fecha;
10. exportar y restaurar en scope aislado.

Implementación:

- contrato neutral y harness async;
- adaptador de referencia sintético, solo para validar la semántica;
- adaptador Firestore inyectable, con transacciones y paths por tenant;
- adaptador PostgreSQL inyectable, con SQL parametrizado;
- esquema PostgreSQL POC con RLS, constraints, unicidad e inmutabilidad de auditoría;
- runner común que solo admite endpoints POC en loopback y proyecto Firestore `demo-*`;
- configuración Firestore aislada, reglas deny-all e índice compuesto declarado;
- tests comunes y guardrails que prohíben rutas a stores/tokens reales.

Estado de ejecución:

| Entorno | Estado | Resultado |
|---|---|---|
| Referencia sintética | Ejecutado | Contrato, aislamiento, duplicado y export/restore aprobados |
| Firestore Emulator | `SUPERADA` | 13/13 operaciones; aislamiento, idempotencia, export/restore; 2 lock timeouts recuperados |

## G. Costes conocidos y UNKNOWN

### Firestore

Conocido según documentación oficial vigente:

- se factura por documentos leídos/escritos/borrados, entradas de índice, almacenamiento
  y transferencia;
- una base por proyecto puede usar cuota gratuita de 1 GiB, 50.000 lecturas/día,
  20.000 escrituras/día, 20.000 borrados/día y 10 GiB/mes de salida;
- TTL, PITR, backups, restore y clones no están incluidos en la cuota gratuita y
  requieren facturación;
- índices incrementan almacenamiento y pueden incrementar lecturas facturables.

UNKNOWN:

- región, edición, patrón de consultas, fan-out de índices, egress y coste mensual OXKIO;
- coste de restore/PITR para el volumen real;
- coste para 10, 100 y 1.000 usuarios.

### PostgreSQL gestionado

Conocido:

- el coste depende del proveedor, región, vCPU/RAM, almacenamiento/IOPS, conexiones,
  HA/réplicas, backups/PITR y red;
- backups y PITR gestionados existen en ofertas como Cloud SQL, pero su coste y
  retención dependen de configuración;
- hay un coste de instancia continuo o una política serverless propia del proveedor.

UNKNOWN:

- proveedor definitivo, edición, tamaño, HA, SLA, región, conexiones y coste;
- coste de backups/exportaciones/restore;
- coste para 10, 100 y 1.000 usuarios.

### Híbrida

Conocido: suma operación, observabilidad, backup y recuperación de dos motores.

UNKNOWN: cualquier ahorro o ventaja para OXKIO; no existe carga que lo demuestre.

No se emite estimación monetaria inventada.

| Metadatos de documentos y Knowledge | PostgreSQL en migración posterior |
| OAuth tokens y secretos | Gestor de secretos futuro; fuera de PostgreSQL |
| Identidad | Firebase Authentication |
| Google Calendar | Google Calendar |
| Documentos/binarios | Drive/OneDrive/almacenamiento de objetos |
| Gobernanza y configuración declarativa | Git |
| Logs técnicos | logging gestionado |
| Fixtures, cachés y temporales | local/test, no producción |

No deben vivir en PostgreSQL:

- claves criptográficas o secretos;
- tokens OAuth en claro;
- binarios/documentos completos si su propietario es Drive/OneDrive/object storage;
- logs técnicos de alta cardinalidad sin política;
- cachés, temporales y fixtures;
- gobernanza que ya es canónica en Git.

No se recomienda híbrida Firestore + PostgreSQL para el núcleo: no hay un tipo de dato
que justifique hoy dos BBDD operativas, y se perdería atomicidad simple entre aprobación,
operación y auditoría. Mantener Calendar, Drive, Firebase Auth y Git en su autoridad
externa no constituye duplicar la persistencia operativa.

## I. Riesgos

1. Las métricas son locales y no predicen rendimiento cloud.
2. Coste, plan y proveedor PostgreSQL todavía `UNKNOWN`.
3. RLS puede ser omitido por roles privilegiados; requiere usuario de aplicación mínimo
   y pruebas de aislamiento.
4. Un pool mal configurado puede agotar conexiones en runtime serverless.
5. Full-text actual no valida relevancia ni idioma con datos reales.
6. OAuth local requiere revocación/rotación y migración a un gestor de secretos.
7. Snapshot JSON contiene estados legacy que deberán normalizarse.
8. Migrar Approval y Operation por separado puede romper idempotencia.
9. Auditoría append-only requiere política de retención y export inmutable.
10. El POC demuestra restore local, no RPO/RTO del proveedor futuro.
11. Knowledge contiene modelos duplicados y rutas locales.
12. El árbol de trabajo contiene cambios ajenos a 5C.7B.2 que deben seguir separados.

## J. Plan de migración y rollback

No se migra todavía. Orden futuro propuesto:

1. Seleccionar proveedor, región, plan, coste, RPO/RTO y SLA.
2. Crear esquema versionado y herramienta de migraciones.
3. Implementar adaptador PostgreSQL productivo detrás de los contratos existentes.
4. Diseñar referencias al gestor de secretos futuro para OAuth.
5. Crear tenant/membresía, usuario mínimo y RLS forzada.
6. Exportar copias read-only de cada JSON con manifiesto, checksum y conteos.
7. Migrar Approval + Operation + Idempotency + Audit como una unidad.
8. Migrar Memory por tenant/user.
9. Migrar agenda ejecutiva, Project Registry, Security Inventory y metadatos.
10. Ejecutar lectura comparada temporal, sin doble escritura.
11. Cambiar la fuente canónica mediante feature flags y ventana aprobada.
12. Probar backup/PITR, restore aislado, export por tenant y salida de proveedor.
13. Ejecutar piloto Cliente Cero con `executionEnabled=false` y SAFE_DRAFT_ONLY.

Rollback:

- desactivar el adaptador remoto;
- detener nuevas mutaciones;
- conservar export y checksums;
- restaurar la última fuente canónica consistente como unidad Approval/Operation/Audit;
- no reintentar efectos con `external_effect_unknown`;
- documentar divergencias antes de reabrir tráfico.
